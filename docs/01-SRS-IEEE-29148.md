## 1. Introducción

### 1.1 Propósito

Este documento especifica los requisitos funcionales y no funcionales del sistema TechMatch.

TechMatch es una aplicación web destinada a ayudar a personas que buscan empleo en tecnología a identificar ofertas laborales compatibles con su currículum vitae, mediante el análisis automatizado de su CV y la comparación determinística con ofertas obtenidas desde fuentes externas a través de sus interfaces públicas (APIs).

### 1.2 Alcance

TechMatch permite:

1. cargar un CV en formato PDF;
2. extraer y procesar su contenido;
3. obtener información estructurada del candidato;
4. comparar dicha información con ofertas laborales;
5. calcular un nivel de compatibilidad;
6. explicar el resultado;
7. mostrar únicamente ofertas con compatibilidad media o alta;
8. adaptar el CV a una oferta, sin inventar datos (`15-ADAPTACION-DE-CV.md`);
9. crear una cuenta opcional con privilegios (`17-CUENTAS-DE-USUARIO.md`);
10. consultar un panel público de tendencias del mercado y, junto a las recomendaciones, las tecnologías más pedidas que el CV no tiene (`18-PANEL-DE-TENDENCIAS.md`).

Las ofertas se obtienen automáticamente desde fuentes que ofrecen una interfaz pública para acceso automatizado: la **API pública de Get on Board** (bolsa de empleo tecnológico de Latinoamérica) y las **APIs públicas de las páginas de empleo** de empresas que publican con **Lever** o **Greenhouse** (`05-FUENTES-DE-OFERTAS.md`).

La sincronización de ofertas se ejecuta cada 12 horas. Después de cada sincronización se recalculan las recomendaciones de todos los CVs analizados.

TechMatch **no realiza scraping** de sitios web: solo integra fuentes que habilitan el acceso automatizado.

### 1.3 Usuarios

* **Visitante:** usa el sistema sin cuenta. Puede subir un CV y ver las primeras recomendaciones.
* **Usuario con cuenta:** se registra con email y contraseña (email verificado). Accede a todas las recomendaciones, a la adaptación del CV y a guardar sus CVs.

La cuenta es opcional. Cualquiera puede cargar más de un CV.

### 1.4 Objetivo

> **Cargar CV → analizar CV → encontrar ofertas compatibles → visualizar recomendaciones explicadas → adaptar el CV a una oferta.**

# 2. Descripción general

## 2.1 Arquitectura conceptual

```text
                    ┌──────────────────────┐
                    │   React (MD3)        │  Cloudflare Pages
                    └──────────┬───────────┘
                               │ HTTP/REST (Authorization: Bearer, opcional)
                    ┌──────────▼───────────┐
                    │  Node.js + TS        │  Render
                    │  API (Express)       │
                    └──┬──────┬──────┬─────┘
                       │      │      │
          Procesamiento   Matching   Cuentas y email
             de CV         engine    (Brevo / Mailpit)
                       │      │      │
                       └──────┼──────┘
                              ▼
                        PostgreSQL (Neon)
                              ▲
                              │
          Sincronización de ofertas (12 h) + recálculo + borrado de CVs vencidos
                              │
                     Conectores de fuentes
                              │
             ┌────────────────┼────────────────┐
             ▼                ▼                ▼
      Get on Board API   Lever (empresas)  Greenhouse (empresas)
```

## 2.2 Tecnologías

### Frontend

React + TypeScript + Vite, con interfaz basada en Material Design 3 (tokens y componentes propios).

### Backend

Node.js + TypeScript (Express 5).

### Comunicación

HTTP/REST. JSON para datos estructurados. `multipart/form-data` para carga de archivos. Sesión por token en el encabezado `Authorization`.

### Persistencia

PostgreSQL, por la naturaleza relacional de los datos.

### Fuentes de ofertas

APIs públicas de portales de empleo y de páginas de empleo de empresas, consumidas mediante conectores.

# 3. Actores

## 3.1 Visitante

Persona que busca oportunidades laborales, sin cuenta.

Puede:

* cargar un CV;
* esperar su procesamiento;
* visualizar las primeras recomendaciones (cantidad configurable) y saber cuántas más hay;
* ver "Qué te falta";
* filtrar las recomendaciones por nivel y modalidad remota;
* consultar el detalle de una oferta;
* acceder a la oferta original;
* consultar el panel de tendencias;
* cargar otro CV;
* crear una cuenta.

No puede:

* ver todas las recomendaciones;
* adaptar el CV;
* guardar CVs;
* editar los datos extraídos;
* postularse desde TechMatch.

## 3.2 Usuario con cuenta

Todo lo del visitante, más:

* ver todas las recomendaciones;
* adaptar el CV a una oferta (borrador, edición, recálculo y PDF);
* guardar CVs en su cuenta y consultarlos en "Mi cuenta";
* borrar CVs guardados y borrar la cuenta;
* recuperar la contraseña por email.

## 3.3 Scheduler

Proceso automatizado (GitHub Actions en producción) que cada 12 horas sincroniza las ofertas, recalcula las recomendaciones y borra los CVs vencidos.

## 3.4 Conectores de fuentes

Componentes que obtienen ofertas desde la interfaz pública de cada fuente y las entregan en un formato común.

## 3.5 Fuentes externas

* Get on Board (API pública v0).
* Páginas de empleo de empresas en Lever (`LEVER_COMPANIES`).
* Páginas de empleo de empresas en Greenhouse (`GREENHOUSE_COMPANIES`).

## 3.6 Servicio de email

Brevo (producción) o Mailpit (desarrollo), para la verificación de email y la recuperación de contraseña.

# 5. Requisitos funcionales

## 5.1 CV

### RF-001 — Carga

El sistema deberá permitir al usuario cargar un CV en formato PDF.

### RF-002 — Validación

El sistema deberá validar que el archivo recibido sea un PDF válido, analizando su contenido y no solo el tipo declarado por el cliente.

### RF-003 — Tamaño

El sistema deberá rechazar archivos cuyo tamaño supere el límite configurado.

### RF-004 — Compresión

El sistema podrá comprimir u optimizar el PDF antes de almacenarlo o procesarlo.

### RF-005 — Extracción

El sistema deberá extraer el texto disponible en el PDF.

### RF-006 — OCR

Cuando el PDF no contenga texto extraíble pero contenga contenido visual legible, el sistema podrá utilizar OCR.

### RF-007 — Información extraída

El sistema deberá intentar identificar:

* experiencia;
* puestos;
* empresas;
* duración;
* años de experiencia;
* educación (un registro por título, con su nivel);
* proyectos;
* skills;
* tecnologías;
* idiomas;
* nivel de inglés;
* seniority;
* ubicación.

### RF-008 — Información faltante

El sistema no deberá inventar información que no pueda determinarse a partir del CV.

### RF-009 — Persistencia

El sistema deberá almacenar el CV procesado y su información estructurada durante un plazo configurable (por defecto 30 días); pasado ese plazo se borran, salvo que el usuario haya elegido guardar el CV en su cuenta. El archivo PDF se borra al terminar el procesamiento y el texto extraído no se guarda: se conserva solo el perfil estructurado.

### RF-010 — Nuevo CV

El usuario podrá cargar otro CV sin autenticarse.

### RF-011 — Edición

El usuario no podrá modificar manualmente la información estructurada del CV. (El CV adaptado es un documento aparte que el usuario edita; ver RF-043.)

### RF-047 — Límite de subidas

El sistema deberá limitar la cantidad de CVs que se cargan desde una misma IP en una ventana de tiempo configurable, respondiendo `429` al superarla.

# 6. Ofertas laborales

### RF-012 — Fuentes

El sistema deberá obtener ofertas laborales de tecnología desde la API pública de Get on Board (categorías configuradas) y desde las APIs públicas de las páginas de empleo de las empresas configuradas en Lever y Greenhouse.

### RF-013 — Acceso autorizado

El sistema solo deberá integrar fuentes que ofrezcan una interfaz para acceso automatizado (API o feed). No deberá extraer datos de páginas web ni evadir bloqueos, CAPTCHAs o controles de acceso.

### RF-014 — Periodicidad

La sincronización de ofertas deberá ejecutarse cada 12 horas. El intervalo deberá ser configurable.

### RF-015 — Datos

El sistema deberá obtener, cuando estén disponibles:

* título;
* empresa;
* modalidad;
* ubicación;
* descripción;
* requisitos;
* conocimientos deseables;
* tecnologías;
* seniority;
* fecha de publicación;
* URL.

### RF-016 — Fuente

Cada oferta deberá almacenar su fuente de origen.

### RF-017 — URL

Cada oferta deberá conservar su URL original.

### RF-018 — Persistencia

Las ofertas deberán almacenarse en la base de datos.

### RF-019 — Duplicados

El sistema deberá evitar almacenar múltiples registros correspondientes a una misma oferta.

### RF-020 — Estado

Cada oferta deberá poder encontrarse en estado:

* activa;
* inactiva.

### RF-021 — Desaparición

Cuando una oferta deje de encontrarse en su fuente, no deberá eliminarse. Deberá marcarse como inactiva.

### RF-022 — Fallo independiente

El fallo de la sincronización de una fuente no deberá impedir la sincronización de otras fuentes.

### RF-048 — Relevancia de las páginas de empresas

De las páginas de empleo de empresas (Lever, Greenhouse) solo deberán guardarse las ofertas de tecnología que sean remotas o en Argentina.

### RF-049 — Recálculo

Después de cada sincronización en la que al menos una fuente termine bien, el sistema deberá recalcular las recomendaciones de todos los CVs procesados contra las ofertas activas.

# 7. Matching

### RF-023 — Algoritmo

El matching deberá utilizar un algoritmo determinístico basado en reglas y ponderaciones.

No se utilizará IA generativa para decidir el resultado.

### RF-024 — Criterios

El matching deberá considerar, cuando exista información suficiente y en este orden de importancia:

1. skills y tecnologías (obligatorias y deseables), solo las del catálogo;
2. seniority;
3. experiencia;
4. educación (valorando carreras afines a informática), idiomas, ubicación y modalidad.

### RF-025 — Score

El sistema deberá calcular un score entre 0 y 100.

### RF-026 — Nivel

El score deberá convertirse en:

* LOW;
* MEDIUM;
* HIGH.

### RF-027 — Filtrado

Las ofertas con nivel LOW no deberán mostrarse al usuario.

### RF-028 — Ordenamiento

Las recomendaciones deberán ordenarse por score descendente.

### RF-029 — Explicación

Cada recomendación deberá incluir las razones que justifican su resultado, una por criterio, con un estado: se cumple, se cumple en parte, no se cumple, o no exigido / no evaluable.

### RF-030 — Determinismo

Para una misma entrada y configuración, el algoritmo deberá producir el mismo resultado.

### RF-031 — Compatibilidad técnica mínima

Una oferta no deberá recomendarse cuando la coincidencia de tecnologías sea inferior al mínimo configurado, aunque el resto de los criterios sumen. Tampoco deberá clasificarse como HIGH si coincide menos del mínimo configurado para ese nivel.

### RF-032 — Modalidad incompatible

Una oferta presencial o híbrida ubicada en otra región o país que la del candidato no deberá recomendarse.

### RF-033 — Score interno

El score numérico es interno: se usa para clasificar y ordenar, pero no se muestra al usuario.

### RF-050 — Seniority lejano

Una oferta cuyo seniority esté a dos niveles o más del candidato no deberá recomendarse.

# 8. Frontend

### RF-034 — Inicio

La portada deberá ser la pantalla de inicio de sesión, con la propuesta del servicio y la opción "Continuar sin cuenta", que lleva a la carga del CV (seleccionándolo o arrastrándolo).

### RF-035 — Procesamiento

El sistema deberá informar al usuario cuando el CV se encuentre siendo procesado.

### RF-036 — Recomendaciones

El sistema deberá mostrar las ofertas compatibles.

### RF-037 — Información

Cada recomendación deberá mostrar:

* título;
* empresa;
* ubicación si existe;
* modalidad si existe;
* nivel de compatibilidad (indicador visual, sin número);
* razones.

### RF-038 — Filtros

El usuario podrá filtrar las recomendaciones por nivel (alta, media) y por modalidad remota, sin alterar el orden por score.

### RF-039 — Detalle

El usuario deberá poder visualizar el detalle de una oferta: requisitos, descripción y tecnologías.

### RF-040 — Fuente

El usuario deberá poder acceder a la oferta original mediante su URL. La interfaz deberá indicar la fuente de las ofertas.

### RF-051 — Qué te falta

Junto a las recomendaciones, el sistema deberá mostrar las tecnologías del catálogo que más exigen las ofertas activas y que no aparecen en el CV, con el porcentaje de ofertas que las piden. Es una sugerencia: no modifica el CV.

### RF-052 — Panel de tendencias

El sistema deberá ofrecer un panel público con métricas agregadas de las ofertas activas (tecnologías más pedidas y por área, seniority, modalidad, fuentes, empresas), sin datos de usuarios ni de CVs.

# 8b. Adaptación de CV (v2.0)

Detalle en `15-ADAPTACION-DE-CV.md`. Desde la v2.1 requiere cuenta.

### RF-041 — Borrador adaptado

Desde una recomendación o el detalle de una oferta, el usuario con cuenta podrá generar un borrador de su CV adaptado a esa oferta.

### RF-042 — No inventar

El borrador solo reordenará, destacará y redactará información presente en el CV. Lo que la oferta pide y el CV no tiene se mostrará como sugerencia y solo se agregará si el usuario lo confirma.

### RF-043 — Edición

El usuario podrá editar el borrador por secciones, con una vista previa en formato Harvard.

### RF-044 — Recalcular

El usuario podrá evaluar el CV editado contra la oferta con el mismo motor de matching, comparando el nivel con el del CV original.

### RF-045 — Exportar

El usuario podrá descargar el CV adaptado en PDF.

### RF-046 — Privacidad del CV adaptado

Los datos personales del CV adaptado (nombre, email, teléfono, links) no se enviarán al servidor. El CV adaptado no se guarda en el servidor (guardarlo está planificado para la v2.4).

# 8c. Cuentas de usuario (v2.1)

Detalle en `17-CUENTAS-DE-USUARIO.md`.

### RF-053 — Registro y verificación

El usuario podrá crear una cuenta con email y contraseña. No podrá iniciar sesión hasta verificar su email mediante un link de un solo uso.

### RF-054 — Sesión

El usuario podrá iniciar y cerrar sesión. Al cerrarla, el token deja de servir.

### RF-055 — Recuperación de contraseña

El usuario podrá restablecer su contraseña mediante un link por email de un solo uso y con vencimiento; al hacerlo se cierran todas sus sesiones.

### RF-056 — Privilegios

Sin cuenta se verán solo las primeras recomendaciones (cantidad configurable). Ver todas, adaptar el CV y guardar CVs requerirán sesión. Los privilegios se aplicarán en la API, no solo en la interfaz.

### RF-057 — CVs guardados

El usuario con cuenta podrá guardar un CV procesado (por decisión propia), verlo en "Mi cuenta" y borrarlo. Un CV guardado solo será visible para su dueño.

### RF-058 — Borrar la cuenta

El usuario podrá borrar su cuenta, confirmando con su contraseña; se borrarán también sus sesiones y sus CVs guardados.

# 9. Requisitos no funcionales

### RNF-001 — Tecnología

Frontend React + TypeScript.

Backend Node.js + TypeScript.

### RNF-002 — Modularidad

Los módulos de fuentes de ofertas, procesamiento de CV, matching, cuentas y email deberán estar desacoplados.

### RNF-003 — Testabilidad

El motor de matching deberá poder probarse independientemente del frontend, de HTTP y de la base de datos.

### RNF-004 — Extensibilidad

Deberá ser posible agregar nuevas fuentes de ofertas agregando un conector, sin modificar el motor de matching.

### RNF-005 — Seguridad

Los archivos deberán validarse antes de ser procesados. Las contraseñas y los tokens (de sesión y de email) se guardarán solo como hash. Los intentos de registro, login y recuperación se limitarán por IP.

### RNF-006 — Privacidad

Los CV almacenados no deberán ser públicamente accesibles ni su contenido registrarse en logs. Las respuestas de la API no deberán revelar qué emails tienen cuenta, salvo el registro de un email ya registrado.

### RNF-007 — Configuración

Los pesos, umbrales, mínimos y parámetros operativos deberán ser configurables.

### RNF-008 — Observabilidad

La sincronización de ofertas, el recálculo, el procesamiento de CV y el envío de emails deberán registrar su resultado y los errores relevantes.

### RNF-009 — Consistencia

La API deberá utilizar contratos de datos definidos.

### RNF-010 — Mantenibilidad

El código deberá utilizar TypeScript estricto y separación de responsabilidades.

### RNF-011 — Interfaz

La interfaz deberá seguir los lineamientos de Material Design 3, ser responsive (escritorio y móvil), usar únicamente el tema claro (sin modo oscuro) y ser accesible (etiquetas, foco visible, movimiento reducido, valores de los gráficos escritos como texto).

### RNF-012 — Uso responsable de fuentes

Los conectores deberán identificarse con un user-agent propio, aplicar timeouts, reintentos limitados y un ritmo de requests moderado. Una respuesta de rechazo (401, 403, 429) no deberá reintentarse.

### RNF-013 — Costo

El sistema deberá poder desplegarse en planes gratuitos (`16-DESPLIEGUE.md`).

# 10. Reglas de negocio

### RN-001

Solo se aceptan CV en formato PDF.

### RN-002

Los matches LOW no se muestran.

### RN-003

La ausencia de información no debe interpretarse automáticamente como cumplimiento ni como incumplimiento.

### RN-004

El sistema nunca debe inventar información del CV.

### RN-005

Las recomendaciones se ordenan por score descendente.

### RN-006

Las ofertas inactivas no deben recomendarse.

### RN-007

Cada oferta conserva fuente y URL.

### RN-008

Un fallo de sincronización no debe eliminar ni desactivar información existente.

### RN-009

El matching debe ser determinístico.

### RN-010

La cuenta es opcional: sin cuenta se puede cargar un CV y ver las primeras recomendaciones. Las funciones exclusivas de la cuenta se controlan en la API.

### RN-011

Solo se integran fuentes con acceso automatizado habilitado; no se hace scraping.

### RN-012

Una oferta sin coincidencia técnica suficiente no se recomienda.

### RN-013

Una oferta presencial o híbrida a la que el candidato no puede trasladarse a diario no se recomienda.

### RN-014

El usuario ve el nivel de compatibilidad, nunca el score numérico.

### RN-015

Solo se comparan tecnologías del catálogo: una etiqueta genérica de la fuente nunca puede aparecer en un CV y no debe contarse como faltante.

### RN-016

Guardar un CV es decisión del usuario; un CV guardado solo lo ve su dueño. Los no guardados se borran pasado el plazo configurado.

### RN-017

Nunca se postula automáticamente a una oferta.
