## 1. Introducción

### 1.1 Propósito

Este documento especifica los requisitos funcionales y no funcionales del sistema TechMatch.

TechMatch es una aplicación web destinada a ayudar a personas que buscan empleo en tecnología a identificar ofertas laborales compatibles con su currículum vitae, mediante el análisis automatizado de su CV y la comparación determinística con ofertas obtenidas desde fuentes externas a través de sus interfaces públicas (APIs).

### 1.2 Alcance

TechMatch permitirá:

1. cargar un CV en formato PDF;
2. extraer y procesar su contenido;
3. obtener información estructurada del candidato;
4. comparar dicha información con ofertas laborales;
5. calcular un nivel de compatibilidad;
6. explicar el resultado;
7. mostrar únicamente ofertas con compatibilidad media o alta.

Las ofertas se obtienen automáticamente desde fuentes que ofrecen una interfaz pública para acceso automatizado. La fuente del MVP es la **API pública de Get on Board**, bolsa de empleo tecnológico de Latinoamérica.

La sincronización de ofertas se ejecuta cada 12 horas.

TechMatch **no realiza scraping** de sitios web: solo integra fuentes que habilitan el acceso automatizado (ver `05-FUENTES-DE-OFERTAS.md`).

### 1.3 Usuarios

El MVP utiliza usuarios anónimos.

No se requiere:

* registro;
* autenticación;
* login;
* sesión persistente;
* perfil de usuario.

Un usuario puede cargar más de un CV durante el uso de la aplicación.

### 1.4 Objetivo del MVP

El objetivo del MVP es proporcionar un flujo simple:

> **Cargar CV → analizar CV → encontrar ofertas compatibles → visualizar recomendaciones explicadas.**

# 3. Actores

## 3.1 Usuario anónimo

Persona que busca oportunidades laborales.

Puede:

* cargar un CV;
* esperar su procesamiento;
* visualizar recomendaciones;
* filtrar las recomendaciones por nivel y modalidad remota;
* consultar el detalle de una oferta;
* acceder a la oferta original;
* cargar otro CV.

No puede:

* editar los datos extraídos;
* acceder a un historial de CV;
* gestionar una cuenta;
* postularse desde TechMatch.

## 3.2 Scheduler

Proceso automatizado que inicia periódicamente la sincronización de ofertas.

## 3.3 Conectores de fuentes

Componentes que obtienen ofertas desde la interfaz pública de cada fuente y las entregan en un formato común.

## 3.4 Fuentes externas

* Get on Board (API pública v0).

# 5. Requisitos funcionales

## 5.1 CV

### RF-001 — Carga

El sistema deberá permitir al usuario cargar un CV en formato PDF.

### RF-002 — Validación

El sistema deberá validar que el archivo recibido sea un PDF válido, analizando su contenido y no solo el tipo declarado por el cliente.

### RF-003 — Tamaño

El sistema deberá rechazar archivos cuyo tamaño supere el límite configurado.

### RF-004 — Compresión

El sistema podrá comprimir u optimizar el PDF antes de almacenarlo o procesarlo.

### RF-005 — Extracción

El sistema deberá extraer el texto disponible en el PDF.

### RF-006 — OCR

Cuando el PDF no contenga texto extraíble pero contenga contenido visual legible, el sistema podrá utilizar OCR.

### RF-007 — Información extraída

El sistema deberá intentar identificar:

* experiencia;
* puestos;
* empresas;
* duración;
* años de experiencia;
* educación;
* skills;
* tecnologías;
* idiomas;
* nivel de inglés;
* seniority;
* ubicación.

### RF-008 — Información faltante

El sistema no deberá inventar información que no pueda determinarse a partir del CV.

### RF-009 — Persistencia

El sistema deberá almacenar el CV procesado y su información estructurada.

### RF-010 — Nuevo CV

El usuario podrá cargar otro CV sin autenticarse.

### RF-011 — Edición

El usuario no podrá modificar manualmente la información estructurada del CV durante el MVP.

# 6. Ofertas laborales

### RF-012 — Fuente Get on Board

El sistema deberá obtener ofertas laborales de tecnología desde la API pública de Get on Board, para las categorías configuradas.

### RF-013 — Acceso autorizado

El sistema solo deberá integrar fuentes que ofrezcan una interfaz para acceso automatizado (API o feed). No deberá extraer datos de páginas web ni evadir bloqueos, CAPTCHAs o controles de acceso.

### RF-014 — Periodicidad

La sincronización de ofertas deberá ejecutarse cada 12 horas. El intervalo deberá ser configurable.

### RF-015 — Datos

El sistema deberá obtener, cuando estén disponibles:

* título;
* empresa;
* modalidad;
* ubicación;
* descripción;
* requisitos;
* conocimientos deseables;
* tecnologías;
* seniority;
* fecha de publicación;
* URL.

### RF-016 — Fuente

Cada oferta deberá almacenar su fuente de origen.

### RF-017 — URL

Cada oferta deberá conservar su URL original.

### RF-018 — Persistencia

Las ofertas deberán almacenarse en la base de datos.

### RF-019 — Duplicados

El sistema deberá evitar almacenar múltiples registros correspondientes a una misma oferta.

### RF-020 — Estado

Cada oferta deberá poder encontrarse en estado:

* activa;
* inactiva.

### RF-021 — Desaparición

Cuando una oferta deje de encontrarse en su fuente, no deberá eliminarse. Deberá marcarse como inactiva.

### RF-022 — Fallo independiente

El fallo de la sincronización de una fuente no deberá impedir la sincronización de otras fuentes.

---

# 7. Matching

### RF-023 — Algoritmo

El matching deberá utilizar un algoritmo determinístico basado en reglas y ponderaciones.

No se utilizará IA generativa para decidir el resultado.

### RF-024 — Criterios

El matching deberá considerar, cuando exista información suficiente y en este orden de importancia:

1. skills y tecnologías (obligatorias y deseables);
2. seniority;
3. experiencia;
4. educación (valorando carreras afines a informática), idiomas, ubicación y modalidad.

### RF-025 — Score

El sistema deberá calcular un score entre 0 y 100.

### RF-026 — Nivel

El score deberá convertirse en:

* LOW;
* MEDIUM;
* HIGH.

### RF-027 — Filtrado

Las ofertas con nivel LOW no deberán mostrarse al usuario.

### RF-028 — Ordenamiento

Las recomendaciones deberán ordenarse por score descendente.

### RF-029 — Explicación

Cada recomendación deberá incluir las razones que justifican su resultado, una por criterio.

### RF-030 — Determinismo

Para una misma entrada y configuración, el algoritmo deberá producir el mismo resultado.

### RF-031 — Compatibilidad técnica mínima

Una oferta no deberá recomendarse cuando la coincidencia de tecnologías sea inferior al mínimo configurado, aunque el resto de los criterios sumen.

### RF-032 — Modalidad incompatible

Una oferta presencial o híbrida ubicada en otra región o país que la del candidato no deberá recomendarse.

### RF-033 — Score interno

El score numérico es interno: se usa para clasificar y ordenar, pero no se muestra al usuario.

---

# 8. Frontend

### RF-034 — Inicio

El sistema deberá mostrar una página de inicio que explique el servicio y permita cargar un CV, seleccionándolo o arrastrándolo.

### RF-035 — Procesamiento

El sistema deberá informar al usuario cuando el CV se encuentre siendo procesado.

### RF-036 — Recomendaciones

El sistema deberá mostrar las ofertas compatibles.

### RF-037 — Información

Cada recomendación deberá mostrar:

* título;
* empresa;
* ubicación si existe;
* modalidad si existe;
* nivel de compatibilidad (indicador visual, sin número);
* razones.

### RF-038 — Filtros

El usuario podrá filtrar las recomendaciones por nivel (alta, media) y por modalidad remota, sin alterar el orden por score.

### RF-039 — Detalle

El usuario deberá poder visualizar el detalle de una oferta: requisitos, descripción y tecnologías.

### RF-040 — Fuente

El usuario deberá poder acceder a la oferta original mediante su URL. La interfaz deberá indicar la fuente de las ofertas.

# 8b. Adaptación de CV (v2.0)

Detalle en `15-ADAPTACION-DE-CV.md`.

### RF-041 — Borrador adaptado

Desde una recomendación o el detalle de una oferta, el usuario podrá generar un borrador de su CV adaptado a esa oferta.

### RF-042 — No inventar

El borrador solo reordenará, destacará y redactará información presente en el CV. Lo que la oferta pide y el CV no tiene se mostrará como sugerencia y solo se agregará si el usuario lo confirma.

### RF-043 — Edición

El usuario podrá editar el borrador por secciones, con una vista previa en formato Harvard.

### RF-044 — Recalcular

El usuario podrá evaluar el CV editado contra la oferta con el mismo motor de matching, comparando el nivel con el del CV original.

### RF-045 — Exportar

El usuario podrá descargar el CV adaptado en PDF.

### RF-046 — Privacidad del CV adaptado

Los datos personales del CV adaptado (nombre, email, teléfono, links) no se enviarán al servidor. En v2.0 el CV adaptado no se guarda en el servidor.

# 9. Requisitos no funcionales

### RNF-001 — Tecnología

Frontend React + TypeScript.

Backend Node.js + TypeScript.

### RNF-002 — Modularidad

Los módulos de fuentes de ofertas, procesamiento de CV y matching deberán estar desacoplados.

### RNF-003 — Testabilidad

El motor de matching deberá poder probarse independientemente del frontend, de HTTP y de la base de datos.

### RNF-004 — Extensibilidad

Deberá ser posible agregar nuevas fuentes de ofertas agregando un conector, sin modificar el motor de matching.

### RNF-005 — Seguridad

Los archivos deberán validarse antes de ser procesados.

### RNF-006 — Privacidad

Los CV almacenados no deberán ser públicamente accesibles ni su contenido registrarse en logs.

### RNF-007 — Configuración

Los pesos, umbrales, mínimos y parámetros operativos deberán ser configurables.

### RNF-008 — Observabilidad

La sincronización de ofertas y el procesamiento de CV deberán registrar su resultado y los errores relevantes.

### RNF-009 — Consistencia

La API deberá utilizar contratos de datos definidos.

### RNF-010 — Mantenibilidad

El código deberá utilizar TypeScript estricto y separación de responsabilidades.

### RNF-011 — Interfaz

La interfaz deberá seguir los lineamientos de Material Design 3, ser responsive (escritorio y móvil), usar únicamente el tema claro (sin modo oscuro) y ser accesible (etiquetas, foco visible, movimiento reducido).

### RNF-012 — Uso responsable de fuentes

Los conectores deberán identificarse con un user-agent propio, aplicar timeouts, reintentos limitados y un ritmo de requests moderado. Una respuesta de rechazo (401, 403, 429) no deberá reintentarse.

# 10. Reglas de negocio

### RN-001

Solo se aceptan CV en formato PDF.

### RN-002

Los matches LOW no se muestran.

### RN-003

La ausencia de información no debe interpretarse automáticamente como cumplimiento ni como incumplimiento.

### RN-004

El sistema nunca debe inventar información del CV.

### RN-005

Las recomendaciones se ordenan por score descendente.

### RN-006

Las ofertas inactivas no deben recomendarse.

### RN-007

Cada oferta conserva fuente y URL.

### RN-008

Un fallo de sincronización no debe eliminar ni desactivar información existente.

### RN-009

El matching debe ser determinístico.

### RN-010

El MVP no requiere autenticación.

### RN-011

Solo se integran fuentes con acceso automatizado habilitado; no se hace scraping.

### RN-012

Una oferta sin coincidencia técnica suficiente no se recomienda.

### RN-013

Una oferta presencial o híbrida a la que el candidato no puede trasladarse a diario no se recomienda.

### RN-014

El usuario ve el nivel de compatibilidad, nunca el score numérico.
